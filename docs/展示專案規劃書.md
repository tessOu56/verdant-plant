# 花草產品體系 — 技術展示規劃書

這份規劃書說明 **Verdant 花草產品體系控制台** 的設計：它是一個純粹的技術能力展示產品，用花草情境呈現三項現代前端核心能力，並用一個 platform 把它們串成可即時查看、可指定啟動的服務體系。

---

## 一、選題原則：每個服務只證明一件事

一個好的技術展示，最怕「什麼都做了一點、但沒有一項夠深」。因此每個服務都對應**一項可被追問到底的前端核心能力**，用花草情境包裝，讓畫面直觀好懂、技術含量卻很紮實。

篩選時用三個問題過濾：這個服務是否對應一項明確的前端能力？能不能就它連問三層技術細節？畫面是否一眼就看得出在做什麼？下面三個服務都通過這三個篩子。

---

## 二、三個展示服務（已實作於 platform）

### 1. 共享花園（即時）— 證明「即時資料流與低延遲」

一個多人共享的花園，伺服器每 6 秒隨機讓一株植物綻放，並持續推播生長事件；使用者點格子澆水讓植物長大。

技術亮點要能講清楚四層：**WebSocket 即時推播**生長與綻放事件；**心跳偵測**（超過閾值沒收到任何訊息就主動斷線重連，而不是傻等）；**指數退避重連**（1s、2s、4s…上限 15s 並加隨機抖動，避免伺服器重啟時的雷鳴羊群）；以及**樂觀更新**（澆水瞬間前端先扣水滴、先讓植物長一階，再等伺服器 `water-ack` 校正）。這四點是即時系統前端的標準能力清單。此服務同時示範 Zustand 管理全域狀態與 TanStack Query 抓取排行榜。

### 2. 花朵綻放 — 證明「重度動畫與像素級渲染」

按「播種」會在 Canvas 上長出一朵程序化的花：花莖生長、花瓣緩動綻放、花粉粒子飄散。

亮點在於它不是 CSS transition 交差，而是一個**用 requestAnimationFrame 驅動、固定時間步長（fixed timestep）的主迴圈**：累積 deltaTime、以固定步長更新邏輯、再繪製，確保不同刷新率的裝置生長速度一致。收合用緩動（easing）而非等速，並提供**低配裝置模式**（降到 30fps、關閉粒子、減少花瓣）示範降階策略。畫面上放一個即時 FPS 讀數，讓人一眼看到對效能的在乎。

### 3. 花圃效能實驗室 — 證明「極端效能優化與記憶體管理」

這個服務最能展現深度，因為它把抽象的「效能優化」變成可對比、可量測的東西。

亮點是**同一份 5 萬筆資料的兩種渲染對比**：全量塞進 DOM（捲動時 FPS 掉到個位數）vs 虛擬列表（只渲染可視區約 30 個節點，維持 60fps），並用即時 FPS 儀表把差距量化。另外內建一個**記憶體洩漏製造器 / 修復器**：故意用未清除的計時器、未移除的 listener、持有大陣列的參照來讓 heap 持續成長，示範如何在 DevTools › Memory 觀察並修復。

### 4. 3D 花園場景 — 證明「WebGL 3D 渲染與互動」

用 Three.js 打造的程序化花田：可拖曳旋轉、滾輪縮放的 OrbitControls 互動相機，花朵隨風搖曳，並提供低多邊形（low-poly）降階模式。重點除了 3D 渲染本身，還在於**離開頁面時確實釋放 geometry / material / renderer**，示範 WebGL 場景如何避免 GPU 記憶體洩漏——這是 3D 前端最容易被追問的地方。

## 三、Platform：把服務串成可即時查看、可指定啟動的體系

三個服務都掛在一個**零依賴的 Node 服務編排控制台**下。控制台本身就是第四個隱藏的展示——因為它同時用到 child process 管理、手刻 WebSocket、即時狀態廣播。

### 運作方式

一個主程序（控制台，埠 4000）負責三件事：提供 dashboard 頁、用 REST 接收啟停指令、用 WebSocket 廣播即時狀態。按下「啟動」時，主程序用 `child_process.spawn` 真的把對應服務的程序拉起來（各自獨立埠號），透過子程序 stdout 印出的 `READY` 判定啟動完成；按「停止」則 `SIGTERM`（3 秒後 `SIGKILL` 保底）。每 2 秒對執行中的服務做一次 **TCP 健康檢查**，把 `status / pid / uptime / reachable` 經 WebSocket 推給 dashboard，所以畫面上看到的狀態都是真實的，不是寫死的。

### 為什麼零依賴、手刻 WebSocket

後端刻意不裝第三方套件，讓已建置的版本 `node server/server.js` 就能跑（免安裝），降低他人現場起跑的門檻。更重要的是 `server/miniws.js` 自己完成了 **RFC 6455 的握手、分幀、遮罩解碼與 ping/pong**——這剛好是 WebSocket 底層最常被追問的部分，等於把「懂不懂 WebSocket 協定」直接寫成可展示的程式碼。

### 架構圖

```
瀏覽器控制台(React) ──REST 啟停──▶ server/server.js（控制台 :4000）
        ▲                            │ child_process.spawn / kill
        └──WebSocket /ws（即時狀態）──┤
                                     ├─▶ garden  :4101（React 頁 + REST 排行 + WebSocket 即時花園）
                                     ├─▶ bloom   :4102（React 頁 · Canvas 動畫）
                                     ├─▶ meadow  :4103（React 頁 · 效能實驗室）
                                     └─▶ scene   :4104（React 頁 · Three.js 3D 場景）
```

### 可延伸性

新增展示服務只需三步：在 `server/` 放一個監聽 `process.env.PORT`、就緒時印 `READY` 的服務檔；在 `server/services.config.js` 加一筆設定；（若要新畫面）在專案根加一個 html 入口與對應的 `src/xxx/main.tsx`，於 `vite.config.ts` 註冊後重新建置。重啟控制台即可在 dashboard 看到並啟動它。所以這個 platform 也是日後累積技術展示的容器。

## 四、技術棧對照

前端完整採用現代 React 生態：**React + TypeScript + Tailwind CSS + Zustand + TanStack Query**，用 Vite 多頁建置。各技術棧的落點：

- WebSocket 可重連 hook（心跳＋指數退避）：`src/lib/useSocket.ts`
- Zustand 全域狀態（花園資源與植株、低配模式）：`src/lib/store.ts`
- TanStack Query 資料抓取（排行榜、服務清單）：`src/lib/api.ts` 搭配 `garden` 與 `platform` 頁
- Tailwind 樣式與自訂色票（leaf / bloom / soil）：各元件 className 與 `tailwind.config.js`
- 手刻 WebSocket 伺服器（RFC 6455）：`server/miniws.js`

後端則刻意維持零第三方依賴，只用 Node 內建模組，兼顧可攜性與底層展示。

---

## 五、建議推進順序

先把「共享花園」打磨到能講清楚四層即時能力（WebSocket 推播、心跳、重連、樂觀更新），這是即時系統最核心的一題；接著補「花圃效能實驗室」，因為它最能撐起追問深度；再把「花朵綻放」與「3D 花園場景」的動畫與渲染細節做細。platform 已可用，四個服務都可從控制台指定啟停，隨技術展示增加持續掛上去即可。
